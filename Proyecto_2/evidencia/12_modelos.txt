Método
--------------------------------------------------------------------------------
- Cada bloque se extrajo de su etiqueta [M1] a [M3] y [V1] a [V6] del script
  a un archivo propio, así que el texto ejecutado coincide byte a byte con el
  bloque.
- Cada bloque se ejecutó primero con --dry_run y luego real, con
  --format=pretty. Se quitaron las líneas "Waiting on bqjob".
- Cada CREATE MODEL se ejecutó con un --job_id determinístico

  bq show --format=prettyjson --model ss2-g16-proyecto2:p2_b_ml.<modelo>
  (campo trainingRuns[].trainingOptions).

  sobre octubre y la comparación entre modelos son de T4

--------------------------------------------------------------------------------
Hallazgo de M-1
--------------------------------------------------------------------------------
- Observado: M-1 tiene eval_loss 124.35 frente a una pérdida de entrenamiento
  de 13.05 (V1), y atribuciones globales de miles en las categóricas con
  trip_distance en 7.33 (V4). M-2, con los mismos datos y L2, mantiene
  eval_loss junto a la pérdida (15.98 y 15.79).
- Hipótesis: la ecuación normal sin regularización (l2Regularization 0) se
  apoya en features colineales. Cada zona pertenece a un solo borough, así
  que las columnas one-hot de borough son combinaciones de las de zona; y
  passenger_missing = TRUE coincide con rate_code_imp = 'NA' en las mismas
  filas (M6, 82,656 filas de la muestra). Con columnas colineales, la
  solución puede tener pesos enormes que se cancelan en entrenamiento y
  fallan en filas con combinaciones poco vistas.
- No se cambiaron hiperparámetros ni datos de M-1: es el modelo con el
  optimizador por defecto que pide la tarea, y M-2 ya es la variante
  regularizada. T4 mide M-1 y M-2 sobre octubre con ML.EVALUATE y confirma o
  descarta la hipótesis.

--------------------------------------------------------------------------------
Notas de diseño
--------------------------------------------------------------------------------
- M1 (familias de modelos): una regresión lineal para fare_amount (M-1 y su
  variante M-2) y una regresión logística para is_high_tip (M-3). Así se
  cubren las métricas de regresión (RMSE, MAE, R²) y de clasificación
  (ROC-AUC, matriz de confusión) que T4 calcula sobre octubre.
- M2 (features): solo las 11 features conocidas al inicio del viaje, con una
  lista explícita en cada SELECT (sin SELECT *). V3 confirma que ningún
  modelo recibió trip_id, pickup_month, split_set, is_eval, payment_type ni
  otra etiqueta.
- M3 (solo tarjeta): M-3 entrena con is_high_tip IS NOT NULL, es decir, solo
  con payment_type '1'; payment_type no es feature.
- M4 (split): M-1 y M-2 usan RANDOM con data_split_eval_fraction = 0.2 sobre
  ene-sep; M-3 usa CUSTOM con is_eval (ene-sep entrena, octubre evalúa).
  Octubre no ajusta pesos en ningún modelo. En M-3 sí sirve para eval_loss y
  para el corte por early_stop, así que influye en cuántas iteraciones hace
  el modelo; sus pesos salen solo de ene-sep. Noviembre ('new') no entra en
  ningún entrenamiento: queda para las predicciones de T5.
- Control de leakage: columnas excluidas (las de M2, verificadas en V3),
  etiqueta de propina solo con tarjeta (M3), split temporal en M-3 (el modelo
  no aprende del futuro) y exclusión previa de los días anómalos 2022-09-17 y
  2022-09-18 en features_trips (V0 de 11_features.txt).
- Diferencias de hiperparámetros entre M-1 y M-2:
  | Opción              | M-1 (m_fare_linreg)       | M-2 (m_fare_linreg_gd)  |
  |---------------------|---------------------------|-------------------------|
  | optimizationStrategy| NORMAL_EQUATION (elegida  | BATCH_GRADIENT_DESCENT  |
  |                     | por AUTO_STRATEGY)        |                         |
  | iteraciones         | 1                         | 20 (máximo, sin corte)  |
  | l2Regularization    | 0                         | 1.0                     |
  | learnRateStrategy   | no aplica                 | LINE_SEARCH (inicial    |
  |                     |                           | 0.1)                    |
  | earlyStop           | no aplica                 | true (min 0.01)         |
  | enableGlobalExplain | true                      | false                   |
  Datos, etiqueta, features y split son iguales.
- M5 (costo): la muestra de 2.48 millones de filas deja cada CREATE MODEL por
  debajo de 0.2 GB facturados; los tres suman 564,133,888 bytes.
